# AnyTLS

依据 AnyTLS 公开协议及 sing-anytls v0.0.8（GPL-3.0-or-later）。TLS 内发送 SHA-256(password)、u16 填充长度和填充；帧为 command:u8 + stream ID:u32 + length:u16（大端）。使用 v1 settings 兼容会话格式；SYN / PSH / FIN 支持同会话多个流，填充方案通过服务端更新帧调整。

会话复用共享有界帧调度器，不共享代理决策：每个 Flow 仍只经 Router 决策一次。与 sing-anytls 一样每个会话同一时间只承载一条流，没有空闲会话就新建（避免无逐流流控时同会话的流互相排队）；会话上限 32（含握手中的会话），满后按负载最小共享，每会话上限 32 条流。新建会话的 TLS 握手不持有池锁，并发进行；名额都在握手中时，新请求等待其中一个完成再选择，整体受 10 秒连接超时约束；待发送队列 8 帧，每流接收队列最多 128 帧且总字节预算 128 KiB；AnyTLS 没有逐流流控，预算满时读取任务等待消费（与 sing-anytls 一样阻塞所在会话），会话里只有这条流时一直等待（与普通 TCP 零窗口相同），同一会话还有其他流被挡住时，等待超过 10 秒才关闭该流。早期实现预算满即关闭流，测速等高速下载会因 lwIP 发送窗口（16 × MSS）暂时排不出而被重置，表现为连接断开重连。填充方案最多 4096 字节、stop 最多 64、每条最多 16 个区间；区间最大 4096。服务端推送的方案按 sing-anytls 的规则宽容解析：没有 `=` 的行、无法解析的区间、不认识的键都忽略，`min > max` 时交换；超过上限的数值按上限截断而不是拒绝；`stop` 缺失或不是数字则该方案无效，保持原方案，**不关闭会话**。不增大内存上限。收到未知命令（含客户端用不到的 Settings、ServerSettings 及 ≥ 11 的命令）时忽略，长度超过 4096 字节的控制帧读取并丢弃，同样不关闭会话，这样服务端新增命令不会让整条会话断开。流 `Drop` 时 FIN 帧发送队列暂时满则后台有界等待（10 秒），超时才中止会话；以前直接中止，一次关闭多条流（测速结束）会让同会话其他流全部断开。空闲清理 interval / timeout / min-idle-session 由配置控制，最多保留 4 个空闲会话。

## UDP

与 sing-box 1.13.14 `protocol/anytls/outbound.go` 相同：UDP 走 sing 的 UDP-over-TCP v2（`common/uot`，sing v0.8.11），承载在会话的一个普通流上。线格式移植在 `oryn-outbound/src/uot.rs`，出处见 [Oryn_dev/docs/oryncore/provenance.md](../../../docs/oryncore/provenance.md)。

- 流目标：`sp.v2.udp-over-tcp.arpa`，端口 0（与 TCP 流相同的 socks5 地址格式）。
- 请求：`isConnect:u8` + socks5 地址。Oryn 总是写 0（逐包寻址，对应 sing 的 ListenPacket），地址为首个目标；请求与第一个数据报合并写出（对应 LazyClientConn）。
- 每包：地址族（`0` IPv4 / `1` IPv6 / `2` 域名，域名为长度 + 字节）+ 地址 + 端口 u16 + 长度 u16 + 载荷，双向相同。
- 载荷最多 65535 字节；接收缓冲最多一个完整帧（65535 + 261 字节）。解析状态留在连接内，`recv_from` 被取消不丢字节；未知地址族、空域名关闭这条 UDP 会话。
- `udp: true` 时启用；UDP 会话占用会话中的一个流，计入每会话 32 流的上限。

sing-box（1.12.8 / 1.13.14）服务端把请求里的首个目标作为这条 UDP 连接的目标：首个目标是域名时由服务端解析，回包来源映射回该域名。之后单个数据报若带有与首个目标不同的域名，sing-box 的 direct 出站不解析，直接关闭整条 UoT 流（sing 自己的客户端也是如此）。Oryn 的 UDP Flow 只向绑定时的目标发送，经 Engine 不会出现这种情况。

测试：线格式与 sing 的 `uot` 解析器逐字节核对（离线 Go 程序），单元测试覆盖碎片读取、取消、65535 字节帧与非法地址族；与 sing-box 1.12.8 / 1.13.14 AnyTLS 入站互通 IP 目标、8000 字节包、以域名为首个目标的会话；p2_engine 走 Engine 的 UDP 路径。

## FIN 语义

AnyTLS 的 FIN 帧关闭**整条流**，不是 smux 那样的半关闭。sing-anytls 服务端（v0.0.11 起）收到 FIN 只在本地关闭，不会回 FIN。所以本端发出 FIN 之后读取立刻视为 EOF，并把该流从会话的流表移除，不再等对端的 FIN。之前按 smux 半关闭处理时，本端写完并关闭后，读取会一直等对端的 EOF（对端不会再发），在 sing-box 1.13.x 上是这条流迟迟不结束。smux / h2mux / yamux 的半关闭行为不变，有单元测试同时覆盖两种语义（`mux/smux.rs`）。UDP 见上，线格式细节见 [uot.md](uot.md)。

## 帧大小

曾把 smux / AnyTLS 每帧的数据上限改成 16376（让帧头加数据正好装进一个 TLS 记录），**已撤销**：调用方一次给 16384 字节，剩下的 8 字节变成一个只有帧头加 8 字节的小帧，帧数翻倍；真机上三个服务端的 AnyTLS 上行都因此掉了约 25%（sing-box 单流 599 → 456、ob-sb 646 → 365，4 流 ~207 → ~149）。

写任务合并写出：写任务取到一帧后，如果队列里已有后续帧（`try_recv`），把它们编码进同一个缓冲、一次写出（上限 32 KiB，两条满帧）。多条流同时上传时每条流的帧可能很小，原来每帧一次 TLS 记录加一次系统调用。AnyTLS 的填充方案只作用在前 `stop` 次写入，填充期间仍逐帧处理，填充结束后才合并。这是对 4 流上行 ~205（单流 ~600）的一个推测性修复：主机上复现不出来，真机上需要看效果。
