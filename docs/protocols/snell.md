# Snell（`type: snell`）

取消安全性专项检查确认 UDP 发送在背压下取消会丢失密文尾部；修复及验证见 [Snell 专项检查](../../../docs/oryncore/audits/audit-snell-2026-10-05.md)。这不等于已证明旧测速日志的唯一根因。

实现在 `oryn-outbound/src/snell/`，移植自 sing-snell（commit 20f2eaec77c3）的客户端部分，出处见 Oryn_dev/docs/oryncore/provenance.md。

## 版本

| 配置 | 线格式 | 说明 |
|---|---|---|
| `version: 4` / `5` | v4 兼容记录 | v5 保留声明版本，但使用 v4 兼容记录层 |
| `version: 6` | v6 记录 | `mode`：`default`（流量画像）、`unshaped`、`unsafe-raw` |
| 缺省或 1–3 | — | 没有可用的独立对端（官方 snell-server 闭源），跳过节点并警告；mihomo 的缺省是 1 |

## 记录层

Oryn 接受用户输入的 Snell v5，保留声明版本，并在基础 TCP/UDP 连接上选择 v4 兼容记录层。记录层的动态分片逻辑仍然生效。Snell v5 专用的 QUIC Proxy Mode（QUIC 流量的 UDP-over-UDP 运行时承载）不在当前实现范围内；这里的 v5 兼容不等于该模式已支持。

- 密钥：Argon2id(PSK, 盐, t=3, m=8 KiB, p=1) 的前 16 字节，AES-128-GCM，nonce 为 12 字节小端计数器。每个方向各自的盐。
- v4：[盐] + 加密首部（版本 4、保留、填充长度、载荷长度）+ 填充 + 载荷密文。只有第一条记录带 256–511 字节初始填充，填充按密文的 0/1 比例生成并与密文按偶数下标交换。分块上限从约 1400 字节起，31 秒内连续写入每次增加 1421，直到 0x3fff。
- v6 default：画像由 BLAKE2b-256(固定种子 ‖ PSK) 派生，包括盐块（盐被打散在带前缀的块里）、每条记录的前缀长度与内容、填充长度（包括把帧长对齐到若干目标长度）、填充内容的四种生成器、填充与密文的三种交换方式、分块策略。全部是 PSK 与记录序号的确定函数，双方各自计算；Go 里的 64 位回绕运算在 Rust 里一律用 `wrapping_*`。首部与载荷分别以前缀 / 填充为附加数据认证。
- v6 unshaped：盐 + 无填充的 v4 式记录，记录最大 0xffff。unsafe-raw：明文首部 + 明文载荷，只应在另一层加密隧道里用。

## 请求与回复

请求：版本 1、命令（TCP 5 / UDP 6）、客户端 ID 长度（0）、TCP 目标（长度前缀主机名 + 端口）。请求与第一段数据在同一条记录里；服务端先说话的应用在读之前单独发出请求。回复是对端第一条记录的首字节：0 隧道（其后即数据）、2 错误（错误码 + 消息）。半关闭写零长记录，不关 TCP。

## reuse

**缺省开启（与 mihomo 的缺省 false 不同）**；写 `reuse: false` 才关闭。原因：云服务器常按「每秒新建连接数」限速（用户的两台轻量服务器实测约每秒 10 个、少量突发，Oryn、官方 sing-snell、mihomo 在 Mac 上结果一致：同时发 32 路时只有约 16 路成功，错开 100 ms 启动则全部成功），超出的连接在发出请求后被服务端直接关闭（`snell: no reply`）；复用把新建连接数降到并发数的量级，同样负载在 40 条/秒下全部成功，并省掉每个请求的一次 TCP 握手（空闲 Ping 低一个往返）。

`reuse: true` 时，双方都收到零长记录后这条 TCP 回到连接池给下一个请求用（同一 TCP 上的密码状态继续）。本端关闭而对端还没结束时，后台丢弃剩余数据直到零长记录（最多 0x80001 字节、10 秒），之后放回池。池最多 10 条、每条最长 180 秒；网络变化 / 唤醒时清空。

取出池内连接前先做一次非阻塞读探测：读到 EOF、错误或任何数据（空闲连接不应有）都视为已失效并丢弃，再尝试下一条，池空则新建。原因是 sing-box 等服务端在交换完零长记录后常常立刻关闭 TCP，而连接要等读到零长记录才放回池，所以放回后很快就会失效；不探测时，并发测速会成批地复用这些死连接，表现为请求在 0.1 秒内 “snell: no reply” 或 “Connection reset by peer”（真机日志）。**新建连接被丢弃时的退避重试**：新建的连接在收到服务端回复之前被关闭 / 重置（EOF、ECONNRESET 等，对应上面的限速），会在新连接上重放已发出的明文，最多重试 4 次，退避 150 / 300 / 600 / 1200 ms 并带最多 50% 的随机抖动，一批连接不会同时重试；超时、协议错误等不重试。实测冷启动一次性 32 路并发：重试前约 16 路成功，重试后 32/32（两轮）；48 路为 43/48、48/48。

探测与实际使用之间仍有竞争窗口（连接刚放回就被下一条流取走，服务端的 FIN 还没到），所以复用来的连接在收到回复之前失败（EOF、重置或写失败）时，会新建一条连接，把此前交给记录层的明文（请求首部 + 数据，最多 64 KiB）在新连接上重放一次；超过上限或已收到回复的流不重放，新建的连接失败也不重试。已失效的连接上服务端根本没读到请求，重放是安全的；理论上若服务端已经转发了首段数据、只是回复丢失，目标会收到两次首段数据，这与其它客户端对复用连接的重试取舍相同。

## UDP

**共用连接**：多个 UDP 会话共用每个出站最多 4 条 Snell UDP 连接（每条最多 128 个会话），按回包来源 `IP:端口` 分发，每个会话一个 64 包的有界队列；最后一个会话结束后连接保留 30 秒，网络变化 / 唤醒时清空。会话的目标在登记前先经完整 DNS 流程解析成 IP（优先 IPv4，与 mihomo 的 UDP 目标解析一致），所以回包归属没有歧义；同一条连接上同一个 `IP:端口` 只登记一个会话，冲突时换连接，都放不下或解析失败时回退到下面的独占连接。原因：真机测速时 UDP 会话有几十到上百个，每个都占一条到节点的 TCP 连接，会和 TCP 争抢服务端按连接数的限制。设计与取舍见 [plan-snell-udp-shared.md](../../../docs/oryncore/plans/plan-snell-udp-shared.md)。本机与 sing-snell v5 服务端互通：40 个会话（IP 与域名目标各半）只建立 2 条 TCP 连接，每个会话收到自己的回显；用户的真实节点 UDP 转发本身不通（官方 sing-snell 客户端同样无回复），所以没有真实节点上的共用验证。

**独占连接**：每个 UDP 会话新建一条连接：发 UDP 请求，读到回复后才收发数据报。包：命令 1 + 地址（IP：0 + 族 4/6 + 地址 + 端口；域名：长度 + 主机名 + 端口）+ 数据；回包：族 + IP + 端口 + 数据（v4 跳过其它族的记录）。超过记录上限的数据报直接丢弃（v4 的上限随分块状态变化）。

## 互通与限制

sing-box 1.14 的 snell 入站：v5（obfs none / http / tls，reuse 开 / 关）与 v6（default / unshaped / unsafe-raw，reuse 开 / 关），TCP 10 B 与 70 KB、顺序短连接（reuse 时服务端接受的 TCP 连接数从 26 降到 18–20）、16 条并发、UDP，错误 PSK。sing-box 的 v5 服务端用流式分块写 UDP 回包，超过约 1400 字节的回包会拆成两条记录，客户端（包括 Go 客户端）收不全；v6 每个数据报一条记录。sing-box 的入站要求 PSK 12–255 字节，客户端不检查。
